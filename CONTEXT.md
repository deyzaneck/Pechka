# Проект "Хлебный Путь" (Driver App) — Контекст для Antigravity 2.0

Ты — специализированный автономный инженер-разработчик и UI/UX проектировщик в проекте **"Хлебный Путь"**. Ваша цель — спроектировать и реализовать минималистичное, высокоэффективное Android-приложение для водителей-экспедиторов хлебобулочных изделий, оптимизированное под жесткие условия работы на маленьких экранах (до 5 дюймов).

---

## 🛑 КРИТИЧЕСКИЕ ОГРАНИЧЕНИЯ И СТЕК ТЕХНОЛОГИЙ
* **Полный OFFLINE:** Приложение работает исключительно на локальной базе данных устройства (SQLite / Room). Никаких облачных синхронизаций в реальном времени во время рейса.
* **Никакого аппаратного оверхеда:** Полностью исключить поддержку NFC, сканирование QR-кодов или геолокационные триггеры. Управление только ручное, через плотные таблицы и крупные touch-таргеты.
* **Целевой интерфейс:** Максимальная плотность данных, крупные элементы ввода (цифровые клавиатуры, оперирование одной рукой), раскрывающиеся списки (Accordion) вместо переходов на новые экраны.

## 📊 БИЗНЕС-ЛОГИКА И ЖЕСТКИЕ КОНСТАНТЫ (HARDCODED)

### Цены и Характеристики Номенклатуры:
* **Хлеб (Белый / Серый):** Цена = 47 руб. / шт. Вместимость 1 лотка = 16 шт.
* **Лаваш:** Цена = 52 руб. / шт. Поставляется строго **ПОШТУЧНО** (понятие лотков для лаваша отсутствует).

### Расчеты и Формулы:
* **Авторасчет стоимости точки:** `Итого = (Кол-во Хлеба * 47) + (Кол-во Лаваша * 52)`.
* **Перевод Хлеба в лотки:** `Лотки = Кол-во Хлеба / 16`.

### Алгоритм "Утреннего умного округления Хлеба":
Если суммарный заказ Хлеба на рейс делится на 16 с остатком (например, 16.5 лотков), приложение инициализирует пре-рейсовый экран:
1. **Выбор направления:** Водитель выбирает `[ В большую сторону ]` (берется целый лоток, возникает излишек в шт.) или `[ В меньшую сторону ]` (урезается партия, возникает дефицит в шт.).
2. **Интерактивное распределение:** На экране выводится список магазинов с кнопками `[+]` и `[-]` только для строки "Хлеб". Водитель обязан вручную поштучно раскидать излишек или вычесть дефицит по конкретным точкам, пока баланс не станет равен `0`.
3. При изменении штук хлеба на точке, ее итоговый чек мгновенно пересчитывается по формуле. Лаваш при этом остается нетронутым.

Для выполнения задач используй подключенные модули в соответствии со следующими сценариями:

* Обязательно пережимай контейнер через `resize_page` под мобильные разрешения (например, 360x640), проверяя, не плывут ли таблицы "Магазин | Хлеб | Лаваш | Оплата".

## 🧠 ИНСТРУКЦИИ ПО ИСПОЛЬЗОВАНИЮ СПЕЦИАЛИЗИРОВАННЫХ СКИЛЛОВ

При работе над кодовой базой и требованиями, строго следуй внутренним инженерным паттернам:

1. **Проработка архитектуры и ТЗ:**
   * Перед написанием кода запусти `to-prd` для фиксации сущностей локальной БД ("Магазины", "Заказы по умолчанию", "Фактические транзакции").
   * Используй режим `grill-me`, чтобы верифицировать граничные кейсы (например, если водитель пытается ввести сумму оплаты больше, чем чек, или оставляет поле пустым).
   * Разбей интерфейс на тикеты через `to-issues` (Экран загрузки рейса -> Главный экран-список -> Блок оплаты в аккордеоне).

2. **Разработка и Прототипирование (Android/Kotlin):**
   * Разворачивай кодовую структуру и управляй сборками через `android-cli`.
   * Применяй `prototype` для быстрой сборки Jetpack Compose UI (или Flutter-компонентов) для экрана интерактивного распределения остатков хлеба.
   * Пиши логику деления и округления лотков через `tdd` (цикл Red-Green-Refactor), чтобы гарантировать отсутствие ошибок округления и потерь копеек.

3. **Диагностика и Рефакторинг:**
   * Если локальная БД SQLite начинает тормозить на старых устройствах при выборке маршрута, вызывай `diagnose` для изоляции проблемы.
   * Для перестроения структуры таблиц без зацепления (decoupling) запрашивай `request-refactor-plan`.

## 🗂️ СТРУКТУРА ДАННЫХ ДЛЯ ЛОКАЛЬНОЙ БД (Ориентир для генерации)
При генерации миграций или Room-сущностей, опирайся на три таблицы:
* `points` (id, name, sequence_order, status ["PENDING", "COMPLETED"])
* `orders` (id, point_id, bread_qty_pieces, lavash_qty_pieces, calculated_sum)
* `payments` (id, point_id, payment_type ["CASH", "CARD"], amount_paid, timestamp)

Переходи к реализации интерфейса и кодовой базы, строго удерживая контекст «Простота, Офлайн, Крупные кнопки».
